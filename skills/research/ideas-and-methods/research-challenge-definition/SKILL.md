# R3｜研究挑战定义与方法映射

## 职责边界

把领域主题转成对象本身的具体失效模式，并判断该问题是否真实、重要、可检验，以及候选方法是否正对该问题。负责问题定义和证据组织；不代替 R2 重做整个分类，不代替 R4 声称已完成基线排名，也不代替 R5 宣称实验复现成功。

## 输入

- 必需：研究对象/系统、拟研究场景、当前方向或候选问题。
- 优先输入：R2 知识地图、代表性原文/代码、可用评估协议。
- 允许独立触发：用户只给出一个方向时，可先澄清边界并形成待验证草案；缺少原始证据不得判定“已确认挑战”。

## 操作步骤

1. **拆解宽泛议题。** 将“鲁棒性、效率、可扩展性、隐私、安全”等宏观词拆成具体对象、条件、失败行为、影响和可观察量。不得把指标名或应用场景直接当成挑战。
2. **写出挑战陈述。** 使用结构：
   > 在【场景/条件】下，【对象/组件】出现【可观测或可推导的失败】，导致【可测影响】；可能机制为【机制/假设】，其证据为【来源/位置】。
   未证实的机制标“假设”，不能写成事实。
3. **操作化验证。** 为每条挑战指定最小观测、指标/证明义务、比较对象、适用边界和反证条件。说明何种结果会推翻这条挑战。
4. **整理证据链。** 分开记录：直接观察/证明、原论文作者解释、自己的推断、反例或相反结果。每个主张附来源定位（论文/版本/页码或图表/代码路径）。通常先核对 2–3 篇最直接相关工作；若领域证据不足，明确缺口，不以固定引用数冒充充分性。
5. **拆解现有方法为何不足。** 对最接近的方法分别说明其假设、适用条件、针对机制、在此场景中的残余失败；不能仅以“作者没研究过”或“指标没有报告”推导方法无效。
6. **建立挑战—方法映射。** 每个候选组件至少对应一条挑战，并写明操作/算子、作用路径、必要性、预测的可观测变化和可能副作用。若多个组件都指向同一挑战，说明职责是否冗余。
7. **检查新颖性与边界。** 搜索/核对相近工作后，区分“问题新”“场景新”“机制新”“组合新”；不得把未检索到直接说成首次提出。将成熟、已解决或缺乏可测影响的问题标出来。

## 交付物

产出《挑战—方法 dossier》，推荐字段：`challenge_id`、对象、场景/条件、失败模式、影响、证据及定位、反证、可检验预测、指标/验证方式、边界、最接近方法、未解决原因、候选组件/算子、组件必要性、预期副作用、待核事项。

每条挑战另给一句话版本；附“保留 / 改写 / 暂缓 / 淘汰”建议和理由。

## 质量门与状态

- **PASS：**对象明确；失效模式具体；证据能定位；有操作化验证与反证条件；最近工作及其局限已公平呈现；每个方法组件有明确对应挑战。
- **PASS_WITH_CAVEATS：**问题可检验，但部分证据、机制或新颖性待核；逐项列出限制。只有下游不依赖未决事项时才允许进入 R4。
- **BLOCKED：**缺少必要材料/评估手段，无法判断挑战是否存在；列明用户需要补充的最小信息。
- **FAIL：**问题仅为宏观标签、被现有证据直接否定、不可证伪，或方法与挑战无可解释关联。

## 回退与交接

- 分类/范围错位 → 回到 `research-knowledge-map`（R2）。
- 关键文献覆盖不足或存在未核反例 → 回到 `research-literature-scout`（R1）。
- 挑战可能已被强基线解决、差距取决于结果口径 → 交 `research-baseline-comparison`（R4）核查。
- 通过后 → 交 `research-baseline-comparison`，携带 dossier 与待比较条件。

交接包统一包含：`project/question/scope`、`source_evidence`、`artifacts`、`gate_status`、`caveats`、`next_skill`、`backtrack_reason`。只交接结论与证据定位，不把未经核验的推断包装为事实。
