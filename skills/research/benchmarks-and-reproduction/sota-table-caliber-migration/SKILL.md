# SOTA 表接入新评测口径 / 换基座

## When to use

- 用户说「以 X 框架/论文为基座，SOTA 表需要修改什么」「把这个新 benchmark 收进表」。
- 现有表的数值口径与新框架不可通约（换基座模型 / 换指标集 / 换聚合方式 / 换评估器）。
- 需要判定新口径下 ★ 给谁，以及旧 ★ 是否迁移。

## 铁律（沿用主表维护约定）

1. **缺数值留 `—`，绝不臆造**；拿不到的数值宁可不落行。
2. **口径不可通约 = 隔离行**，禁止跨口径取最优、禁止混排加粗。
3. **★ 迁移三条件**：一致口径 + 严格占优 + 正式发表或第三方复现。**新开口径轨时，该轨首名可直接标 ★，但必须在备注写明聚合方案与适用条件。**
4. **单一源**：主表只保留 `实验与SOTA/` 一份，不向方向文件夹同步副本。
5. 所有数值**逐字取自原文表格并注明表号/页码**，抽取后必须回查。
6. 🔒 **维护范围铁律（2026-08-31 用户确立，最重要）**：本表**只维护「不同方法 × 同一基准」的实验指标数据**——行的主体必须是**方法**（或方法×基准组合）。**评测基准/框架自身的数据一律不落表**，典型即「行对象是评估指标」的元评估表（如 OpenUnlearning Table 2 的 12 指标元评估、Table 5 的 probing）——那是对指标本身的体检，不是方法在基准上的表现。新开口径轨时先筛掉这类表；若其中确有决策价值的结论（如「哪些指标可靠」），**降级为系列末尾的 📌 注记**（一句话结论 + 出处），**绝不重建指标级表格**。系列头部必须写一条「维护范围」声明，防止后续会话误重建。

## Steps

1. **抽取新框架原文口径**（PDF 用 PyMuPDF，`/Users/chenyliao/.workbuddy/binaries/python/envs/default/bin/python` 已装 pymupdf；Read 工具对部分 PDF 无效）：
   - 抓 4 件事：`基座模型`（含是否弃用旧基座）、`任务/数据划分`、`指标集合与聚合公式`、`调参与选模策略`。
   - 命令范式：`python -c "import pymupdf; d=pymupdf.open(PDF); open(OUT,'w').write('\n'.join(f'===PAGE {i+1}===\n'+p.get_text() for i,p in enumerate(d)))"` 再 grep/sed 定位表。
   - ⚠️ 表格数值常被 PDF 抽取**拆成单列多行**，且附录/末页表格易被截断（先 `wc -l` 再 `tail` 确认拿到了全部行）。
2. **反算验证聚合公式**：拿到主表数值后，用公式反算至少 2 个方法（一个高分一个低分）的聚合值，确认与原文一致。这能同时验证公式理解与数值抄写。**做不完这步不许落表。**
3. **列「不可通约维度」清单**：逐维对比新口径 vs 主表主口径，至少覆盖 **基座 / 指标集 / 主判定指标是否缺失 / 基准覆盖** 四项；外加两条框架自承的坑（跨基准实现不一致、评估器版本差异）。用 SVG 两栏对比图呈现给用户，比文字表更直观。
4. **排 8 处 patch**（P1–P8 标准清单）：
   - P1 字段规范版本升级（列序定义，新口径列装不进旧列序就必须先升级）
   - P2 新增子表（落官方数值，含基线行与金标准行，基线行标"不参与排名"）。**若该论文有多张实验表要全量收编，直接建「系列子表」而非单表**：`## Table_<前缀>` 下挂 `### A表-1 / A表-2 / A表-3 …`，系列头部放**索引表（编号/对应原表/行对象/列数）+ 共享口径声明 + 硬性警示**。每张表各自保留 v4 列序与独立表头，便于逐列对照与单独引用。
   - P3 判定节新增该口径 ★ 行，并细分口径说明（两套→三套）
   - P4 各 B 表换轨（基座/指标/SOTA 取值行/超参列，含**评估器 commit hash** 列）
   - P5 方法全景条目精修
   - P6 维护说明书加插入规则
   - P7 风险清单新增条目
   - P8 卷首核验范围声明修订
5. **问用户两件事再动手**：① 基座档位（对齐官方数值的最小档 / 量级可比的大档 / 双轨）；② 执行范围（只落数值 / 全量换轨 / 暂不改）。**不要自作主张全量改。**
6. **落表**：子表头部必须写全「口径定义 + 聚合公式 + 硬性警示」，末尾写「本方向的落点结论」（如适应度该用哪些指标）。
7. **变更日志**：追加 `㊸` 式编号条目，写清数据来源、做了什么、**挂账了什么**（未做的 patch 逐条列出）。
8. **结构校验**（必做）：脚本扫全文 markdown 表格块，统计每块列数集合，异常块必须为 0。
   ```python
   blocks=[];cur=[]
   for i,l in enumerate(lines,1):
       if l.strip().startswith('|'): cur.append((i,l))
       else:
           if cur: blocks.append(cur); cur=[]
   for b in blocks:
       c={len(l.strip().strip('|').split('|')) for _,l in b}
       if len(c)>1: print('异常块', b[0][0], c)
   ```
   **先跑分隔行自愈再校验**（加列/重排列后必做）：表头改了、分隔行 `|---|` 极易漏同步（同一块里只有分隔行列数少 1 是最高频异常）。
   ```python
   for i,l in enumerate(lines):
       s=l.strip()
       if s.startswith('|') and set(s.replace('|','').replace(' ','')) <= {'-'} and '-' in s:
           prev=lines[i-1].strip()
           if prev.startswith('|') and len(s.strip('|').split('|')) != len(prev.strip('|').split('|')):
               lines[i] = '|' + '---|' * len(prev.strip('|').split('|'))
   ```
9. **提交推送**：仓库根 = `实验与SOTA`，remote `git@github.com:guts-yang/mu_papers_table.git`。
   - 先 `git pull`（有未提交改动会失败，先 commit 或 stash）；确认 `HEAD == origin/main` 再推。
   - commit 格式：`docs(unlearning): <中文描述> --story`（沿用仓库既有风格，后缀 `--story`）。

## Pitfalls

- **聚合方案会让排名整体反转**：同一批 checkpoint 换聚合维度（如三维 HM → 二维 HM）可让第一名与垫底互换。必须**双录**两套聚合结果，并在备注写明机理（例如剔除隐私维度后"过度遗忘"不再受罚）。★ 只在你选定的那套聚合下成立。
- **框架不实现旧主指标**：新框架往往不报主表的核心判定指标（如 OpenUnlearning 不报 FQ，FQ 不在其元评估 12 指标内）→ 不可用旧指标当新口径的适应度/目标，也不能换算。
- **同一方法名跨基准实现不同**：框架论文常自承（如 NPO 在 TOFU 与 MUSE 公式不同、UNDIAL 三基准皆未实现）。填表时"同一方法名"必须标变体，否则跨行比较是假比较。
- **评估器版本差异**：同一 checkpoint 在不同评估器下指标可差数倍（OU 评估器 vs pipeline 评估器 MU 0.44 vs 0.27）→ 自跑数值必须标注评估器 commit hash。
- **框架只在部分基准给了数值**：如 OU 只在 TOFU 上给了方法对比，MUSE/WMDP 只有框架支持 → 相应子表在新口径下**无参考行可填**，这是空洞不是遗漏，要提前告知用户。
- **调参预算不对称**：框架常给每方法 N 次调参 trial（OU=27）。未按同预算复现的方法行**禁止**与框架官方行并列比。
- 正文与表格自相矛盾是常态（如声称每类 100 题、表内实为 50）→ 以表为准并在备注记录矛盾。
- **改表头 = 改全表**：加列/重排列时，除了表头与数据行，**分隔行 `|---|` 必须同步重建**。用自愈脚本统一处理，不要手改（2026-08-31 B 表重排 5 张，3 张分隔行漏一列）。
- **A/B 表列序要对齐**：B 表（我的实验表）若缺 A 表的信息列（全称 / 年份·出处），两表无法逐列对照。当前规范 v4：两表前缀同为 `基座名称｜SOTA｜代码链接｜方法｜指标…｜全称｜年份/出处`，A 表尾接 `数据来源｜设置一致性`，B 表尾接 `Batch｜LR｜Epoch｜GPU型号×数量`。**B 表不设数据来源/设置一致性两列**（用户 08-20 决定，自跑数据来源即本表）。
- **行对象不是"方法"的表 → 直接不落（2026-08-31 教训）**：基准论文的**元评估表**（评估指标的可信度，如 OU Table 2 的 12 指标、Table 5 的 probing）行对象是指标而非方法。曾尝试「保留 v4 列序、把『方法』列位改名为『指标』」来收编，**用户最终要求整段删除**——本表维护的是「方法 × 基准」的指标，不维护基准自身的体检数据。做法：这类表**整表不落**，只把其中对本研究有决策价值的结论（如「哪些指标可靠、哪些会崩」）**降级为一张 📌 注记**写在系列末尾（结论 + 出处，不入表）。**删除后必须同步清理四类外部引用**：系列头索引表、速览块、字段规范段（列数说明 + 指标定义）、1.2 节指向句；否则会留下指向已删表的悬空引用。
- **多 ★ 口径必须显式隔离**：同一批 checkpoint 因聚合方案不同产生两个第一名时，**两个 ★ 都要标但必须带口径后缀**（如 `★(Agg)` vs `★(Agg-2D)`），并在表头写「不得互比或合并引用」。只标一个会让读者误以为结论唯一。
- **框架论文自身也有内部不一致**：官方表之间同值不同精度（T3 `3e-3` vs T6 `3.27e-03`）、基线行在后续表中沿用旧值未重算（Retain 的 Agg 在 T6 沿用 T3 的 0.58，按新公式应为 0.47）。落表时**统一取更精确值并注明原表记法**，不要默默选一个。

## Verification

- 聚合公式反算命中 ≥2 个方法。
- 全文表格块列数异常数 = 0。
- 每个新数据行都有：`数据来源`（带表号）、`设置一致性`（含口径与调参信息）、出处链接。
- 变更日志已追加，未做的 patch 已挂账。
- `git log --oneline -2` 显示新 commit 且 `HEAD == origin/main`。
